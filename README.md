# Webhook Provider Platform

A reliable webhook delivery platform built with Django REST Framework, Celery, Redis, and PostgreSQL. The system allows users to register webhook endpoints, subscribe to specific event types, and receive signed event notifications asynchronously.

The project implements webhook concepts commonly used by platforms such as payment providers, developer APIs, and SaaS applications, including HMAC request signing, asynchronous delivery, delivery tracking, retries, and failure handling.

## Overview

The Webhook Provider Platform allows applications to register HTTP endpoints and subscribe to events generated by the platform.

When an event occurs, the system determines which webhook endpoints belong to the event owner and are subscribed to that event type. A separate delivery record and Celery task are then created for each matching webhook.

This prevents one unavailable or failing webhook endpoint from blocking deliveries to other endpoints.

For example:

```text
User A
├── Webhook 1 → payment.confirmed
└── Webhook 2 → payment.confirmed

User B
└── Webhook 3 → payment.confirmed
```

If a `payment.confirmed` event belongs to User A, only User A's subscribed endpoints receive the event. User B does not receive another user's event.

## How It Works

A client first registers a webhook URL and specifies the events it wants to receive.

Example:

```json
{
    "url": "https://example.com/webhook/",
    "events": [
        "payment.confirmed"
    ]
}
```

When an event occurs:

```python
Event.objects.create(
    user=user,
    event_type="payment.confirmed",
    payload={
        "amount": 500,
        "product": "shoe"
    }
)
```

the platform finds active webhook endpoints belonging to that user that are subscribed to `payment.confirmed`.

Each matching endpoint receives a payload similar to:

```json
{
    "event": "payment.confirmed",
    "data": {
        "amount": 500,
        "product": "shoe"
    }
}
```

## Webhook Security

Each registered webhook endpoint is assigned a secret.

Before sending an event, the platform serializes the payload and generates an HMAC-SHA256 signature using the webhook secret.

Example:

```python
signature = hmac.new(
    webhook.secret.encode(),
    payload_string.encode(),
    hashlib.sha256
).hexdigest()
```

The signature is included in the request headers:

```text
X-Webhook-Signature: <generated-signature>
```

The receiving application can calculate its own signature using the shared webhook secret and compare it against the received signature.

This allows clients to verify that the webhook was generated by a party that possesses the webhook secret and that the signed request body has not been modified.

## Asynchronous Delivery

Webhook requests are not delivered directly inside the original HTTP request cycle.

Instead, each delivery is queued as an independent Celery task:

```text
Django
   |
   | sendrequest.delay(delivery_id)
   v
Redis
   |
   v
Celery Worker
   |
   v
Client Webhook
```

This prevents slow or unavailable third-party servers from delaying the main API.

It also isolates webhook failures.

For example:

```text
Delivery A → 200 OK
Delivery B → Connection Error
Delivery C → 200 OK
```

Delivery B can fail or retry without preventing A or C from completing.

## Delivery Tracking

Each webhook attempt is represented by a delivery record.

A delivery stores information such as:

```text
Event
Webhook Endpoint
Status
Number of Attempts
HTTP Response Status
Last Error
Created At
Updated At
```

Possible delivery states include:

```text
pending
success
failed
dead
```

Failed deliveries can be retried, while deliveries that exceed the configured retry limit can be marked as dead for later inspection.

## Client Application

A separate repository called **`webhook_client`** was created to simulate a real application consuming webhooks from this platform.

The client application exposes its own webhook endpoint and:

- Receives webhook POST requests
- Reads the `X-Webhook-Signature` header
- Uses the shared webhook secret to generate its own HMAC-SHA256 signature
- Compares the generated signature with the received signature
- Rejects requests with missing or invalid signatures
- Accepts successfully verified webhook events

This makes it possible to test the complete webhook lifecycle using two independent applications:

```text
Webhook Provider                    webhook_client

Django API
     |
     | Create Event
     v
Celery / Redis
     |
     | HMAC signed POST
     |---------------------------->
                                  Client API
                                      |
                               Verify Signature
                                      |
                                +-----+-----+
                                |           |
                              Valid       Invalid
                                |           |
                              200         401
```

The two projects can be run independently on different ports during local development.

Example:

```text
Webhook Provider:
http://127.0.0.1:8000/

Webhook Client:
http://127.0.0.1:9000/
```

A client webhook can therefore be registered as:

```text
http://127.0.0.1:9000/client/
```

## Installation

Clone the repository:

```bash
git clone <repository-url>
cd <repository-directory>
```

Create a virtual environment:

```bash
python -m venv venv
```

Activate it on Windows:

```bash
venv\Scripts\activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

Run migrations:

```bash
python manage.py makemigrations
python manage.py migrate
```

## Redis

Redis is used as the Celery message broker and can be run with Docker.

Example:

```bash
docker run -d -p 6379:6379 redis
```

For a Django/Celery process running directly on the host machine:

```python
CELERY_BROKER_URL = "redis://localhost:6379/0"
CELERY_RESULT_BACKEND = "redis://localhost:6379/0"
```

## Running the Application

Start the Django development server:

```bash
python manage.py runserver 8000
```

Start the Celery worker:

```bash
celery -A project worker -l INFO
```

When developing on Windows, the solo worker pool can be used:

```bash
celery -A project worker -l INFO --pool=solo
```

Ensure Redis is running before starting the Celery worker.

## Testing Webhook Delivery

The project can be tested using either:

1. The separate `webhook_client` repository
2. A webhook inspection service such as Webhook.site

Using `webhook_client` provides a more complete test because it allows both webhook delivery and HMAC signature verification to be tested.

A typical test flow is:

```text
1. Start Redis
2. Start the webhook provider
3. Start the Celery worker
4. Start webhook_client on port 9000
5. Register the client's /client/ URL
6. Subscribe the endpoint to an event
7. Create the event
8. Celery receives the delivery task
9. Provider signs the payload
10. Provider POSTs the event to webhook_client
11. webhook_client verifies the signature
12. Provider records the HTTP response
```
